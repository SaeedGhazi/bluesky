# راهنمای جامع پوشه‌ی Navaids و NavData در FlightGear

> مرجع کامل ساختار، فرمت و کاربرد فایل‌های داده‌ی ناوبری در FlightGear — هم پوشه‌ی
> مرکزی `$FG_ROOT/Navaids/`، هم پوشه‌ی `NavData/` داخل یک scenery اختصاصی.
>
> این سند با **استخراج مستقیم از داده‌ی واقعی** (`fgdata/Navaids/*.dat.gz`،
> `fgdata/Airports/apt.dat.gz` شامل فرودگاه واقعی OIII مهرآباد، و **AIP رسمی
> OIII/OIIE** سازمان هواپیمایی کشوری ایران) و **سورس‌کد**
> (`flightgear/src/Navaids/NavDataCache.cxx`, `navrecord.cxx`,
> `src/Airports/apt_loader.cxx`, `terragear/src/Airports/GenAirports/lights.cxx`)
> نوشته شده است. فرمت‌ها مبتنی بر استاندارد داده‌ی X-Plane (که FlightGear از آن
> استفاده می‌کند) هستند.
>
> پوشش: پوشه‌های `Navaids/` و `Airports/`، پوشه‌ی `NavData/` در scenery، تبدیل
> داده‌ی AIP به فرمت FlightGear، محدودسازی حجم داده برای کارایی، و رابطه‌ی
> WED/`.btg`/TerraGear.

## ۱. مفهوم کلی

تمام «جهان ناوبری» FlightGear — هر فرودگاه، باند، VOR، NDB، ILS، فیکس، مسیر هوایی —
از چند **فایل متنی با فرمت X-Plane** خوانده می‌شود. این فایل‌ها:

- معمولاً با `gzip` فشرده‌اند (`.dat.gz`) برای صرفه‌جویی فضا.
- توسط زیرسیستم‌های زیر مصرف می‌شوند: route-manager، autopilot، GPS/FMS، نقشه
  (Map/ND)، سیستم ATC و AI traffic، و dialogهای planner.
- در بدو اجرا یک‌بار parse و به **یک کش باینری SQLite** (`navdata.cache`) تبدیل
  می‌شوند تا دفعات بعد سریع لود شوند.

دو محل وجود دارد:

| محل | نقش |
|-----|-----|
| `$FG_ROOT/Navaids/` و `$FG_ROOT/Airports/` | داده‌ی **پیش‌فرض جهانی** (کل کره‌ی زمین) |
| `<scenery>/NavData/<type>/*.dat[.gz]` | داده‌ی **اختصاصی/override** برای یک منطقه/فرودگاه |

## ۲. NavDataCache — قلب سیستم

> مرجع: `src/Navaids/NavDataCache.cxx`، تابع `findDatFiles()`.

هنگام راه‌اندازی، FlightGear برای هر «نوع داده» (`apt`, `awy`, `nav`, `fix`,
`poi`, `TACAN_freq`) این الگوریتم را اجرا می‌کند:

```
برای هر نوع داده T:
  ۱. برای هر مسیر scenery در fg_scenery:
        اگر پوشه‌ی  <scenery>/NavData/T/  وجود داشت:
            همه‌ی *.dat و *.dat.gz آن را (به‌ترتیب الفبایی) به لیست اضافه کن
  ۲. در انتها، فایل پیش‌فرض را اضافه کن:
        apt   → $FG_ROOT/Airports/apt.dat.gz
        nav   → $FG_ROOT/Navaids/nav.dat.gz
        fix   → $FG_ROOT/Navaids/fix.dat.gz
        awy   → $FG_ROOT/Navaids/awy.dat.gz
        poi   → $FG_ROOT/Navaids/poi.dat.gz
        carrier      → $FG_ROOT/Navaids/carrier.dat.gz
        TACAN_freq   → $FG_ROOT/Navaids/TACAN_freq.dat.gz
        metar        → $FG_ROOT/Airports/metar.dat.gz
```

نکات کلیدی که از کد بیرون می‌آید:

- **فایل‌های scenery اول، فایل پیش‌فرض آخر.** پس داده‌ی scenery شما **قبل از**
  داده‌ی جهانی خوانده می‌شود → امکان override/تکمیل.
- نام پوشه دقیقاً همان «نوع» است: `NavData/apt/`, `NavData/nav/`, `NavData/fix/`,
  `NavData/awy/`, `NavData/poi/`.
- کش وقتی بازسازی می‌شود که **تعداد، ترتیب، مسیر واقعی (realpath) یا زمان تغییر
  (modtime)** هر فایل منبع عوض شود (`areDatFilesModified()`). یعنی فقط اضافه‌کردن
  یک فایل به `NavData/apt/` کافی است تا در اجرای بعد، کش خودکار rebuild شود.

> ⚠️ به همین دلیل، بعد از ویرایش داده‌ی ناوبری ممکن است یک‌بار «Rebuilding
> navigation database» در splash ببینی — طبیعی است.

## ۳. نمای کلی پوشه‌ی `Navaids/`

محتوای واقعی `fgdata/Navaids/`:

```
Navaids/
├── nav.dat.gz          ← NDB, VOR, ILS, DME, TACAN, Marker beacons   (~26.8K خط)
├── fix.dat.gz          ← فیکس‌ها / تقاطع‌های IFR                       (~119K خط)
├── awy.dat.gz          ← مسیرهای هوایی (low/high airways)             (~70K خط)
├── poi.dat.gz          ← نقاط مورد علاقه (کشور/شهر/روستا از OSM)       (~769K خط)
├── carrier_nav.dat.gz  ← TACAN ناوهای هواپیمابر (متحرک)
├── TACAN_freq.dat.gz   ← جدول کانال TACAN → فرکانس پاسخ
├── range.high          ← جدول ارتفاع↔برد دریافت (VOR ارتفاع‌بالا)
├── range.low           ← جدول ارتفاع↔برد (VOR ارتفاع‌پایین)
├── range.term          ← جدول ارتفاع↔برد (Terminal)
├── Antennas/           ← الگوی پرتو آنتن (Yagi) برای مدل‌سازی دریافت
│   ├── yagi4.txt
│   └── yagi41.txt
└── ReadMe.FG226.txt    ← توضیح نسخه و changelog داده
```

> توجه: فایل `apt.dat.gz` (فرودگاه‌ها) عضو پوشه‌ی **`Airports/`** است نه
> `Navaids/`، اما بخشی از همین سیستم است (بخش ۱۳).

## ۴. `nav.dat`

مهم‌ترین فایل ناوبری. هر خط یک «navaid» است. خط اول فایل یک عدد نسخه + متن لایسنس
GNU است (مثلاً `810 Version - data cycle 2013.10 ...`). سپس رکوردها.

### ۴.۱ کد نوع رکورد (ستون اول)

| کد | معنی | تعداد در داده‌ی واقعی |
|----|------|----------------------|
| `2` | NDB (Non-Directional Beacon) | 7099 |
| `3` | VOR / VOR-DME / VORTAC (جزء VOR) | 3720 |
| `4` | ILS Localizer (cat I/II/III) | 3202 |
| `5` | Localizer تنها (LOC، بدون GS) | 299 |
| `6` | Glideslope (GS) | 3197 |
| `7` | Outer Marker (OM) | 1617 |
| `8` | Middle Marker (MM) | 1612 |
| `9` | Inner Marker (IM) | 211 |
| `12` | DME (جزء DME؛ مثل DME-ILS یا VOR-DME) | 5043 |
| `13` | TACAN / جزء DME در VORTAC | 771 |

### ۴.۲ فرمت ستون‌ها (نمونه‌های واقعی)

```
کد  عرض‌جغرافیایی    طول‌جغرافیایی   ارتفاع  فرکانس  برد  جهت/واریاسیون  شناسه  [ICAO رانوی]  نام
─────────────────────────────────────────────────────────────────────────────────────────────
2   38.08777778  -077.32491667     0    396   50    0.0           APH                A P HILL NDB
3   57.10371900   009.99557800    57  11670  100    1.0           AAL                AALBORG VOR-DME
4   39.98091100  -075.87781400   660  10850   18    281.662       IMQS 40N  29       ILS-cat-I
5   40.03460600  -079.02328100  2272  10870   18    236.086       ISOZ 2G9  25       LOC
6   39.97729400  -075.86027500   630  10850   10    300281.700    IMQS 40N  29       GS
7   39.96071900  -075.75077800   660      0    0    281.700       ---- 40N  29       OM
12 -09.43270300   147.21644400   128  11010   18    0.200         IWG  AYPY 14L      DME-ILS
13  57.10393300   009.99280800    57  11670  199    0.0           AAL                AALBORG TACAN
```

**معنی ستون‌ها:**

| ستون | توضیح |
|------|-------|
| ۱ | کد نوع (جدول بالا) |
| ۲ | عرض جغرافیایی (درجه، اعشاری) |
| ۳ | طول جغرافیایی (درجه، اعشاری) |
| ۴ | ارتفاع آنتن (فوت، MSL) |
| ۵ | **فرکانس** — NDB: کیلوهرتز (396 = 396kHz). VOR/ILS/DME: ده‌هزارم مگاهرتز یعنی `11670 = 116.70 MHz`، `10850 = 108.50 MHz` |
| ۶ | **برد** دریافت (مایل دریایی، NM) |
| ۷ | فیلد جهت — برای VOR: slaved magnetic variation. برای LOC/ILS (کد 4/5): **بیرینگ باند مغناطیسی**. برای GS (کد 6): **زاویه‌ی glideslope ×۱۰۰ + بیرینگ** (مثلاً `300281.700` = شیب 3.00° و بیرینگ 281.700) |
| ۸ | شناسه (ident) — مثل `AAL`, `IMQS` |
| ۹+ | برای ILS/LOC/GS/Marker: ICAO فرودگاه + شماره‌ی باند (مثل `40N 29`)، سپس نام/نوع |

> 💡 یک ILS کامل = چند رکورد جدا: یک `4` (localizer) + یک `6` (glideslope) + گاهی
> `7/8/9` (markerها) + یک `12` (DME). همگی با همان فرکانس به هم مرتبط می‌شوند.

> 💡 یک `VOR-DME` = یک رکورد `3` (VOR) + یک رکورد `12/13` (DME) با همان شناسه.
> یک `VORTAC` = رکورد `3` + رکورد `13`.

## ۵. `fix.dat`

فیکس‌ها (waypointهای نام‌دار IFR / تقاطع‌ها) که در مسیرهای هوایی و SID/STAR استفاده
می‌شوند. فرمت بسیار ساده: خط اول `I` (ترتیب بایت) و خط دوم نسخه، سپس:

```
عرض‌جغرافیایی   طول‌جغرافیایی   شناسه
─────────────────────────────────────
 19.935017   -158.944997   00HNL
 22.528056   -156.170961   00MKK
 00.000000    045.000000   0045E
```

| ستون | توضیح |
|------|-------|
| ۱ | عرض جغرافیایی (درجه اعشاری) |
| ۲ | طول جغرافیایی (درجه اعشاری) |
| ۳ | شناسه‌ی فیکس (۵ کاراکتری استاندارد ICAO مثل `BITTA`، یا کدهای مختصاتی مثل `0045E`) |

فایل به `99` ختم می‌شود (نشانه‌ی پایان). ~119 هزار فیکس در داده‌ی پیش‌فرض.

## ۶. `awy.dat`

مسیرهای هوایی — هر خط یک **قطعه (segment)** بین دو waypoint است. فرمت X-Plane 640.

```
شروع    عرض‌شروع     طول‌شروع    پایان   عرض‌پایان    طول‌پایان   نوع  کف   سقف  نام‌مسیر
──────────────────────────────────────────────────────────────────────────────────────
00MKK 22.528056 -156.170961 BITTA 23.528031 -155.478836  1  012  460  R464
00UPP 20.566668 -154.125000 BYROW 20.369456 -155.058992  1  140  460  R578
03SML 25.610000  030.635278 AST   27.031222  031.032500  1  085  600  W8
```

| ستون | توضیح |
|------|-------|
| ۱–۳ | شناسه، عرض، طول waypoint **شروع** قطعه |
| ۴–۶ | شناسه، عرض، طول waypoint **پایان** قطعه |
| ۷ | نوع/جهت قطعه (`1` = airway کم‌ارتفاع/Victor در این داده؛ مقدار بالاتر = پرارتفاع/Jet) |
| ۸ | **کف** مجاز (Flight Level، مثلاً `012` = FL012، `085` = FL085) |
| ۹ | **سقف** مجاز (Flight Level، مثلاً `460` = FL460) |
| ۱۰ | نام مسیر هوایی — مثل `R464`, `W8`, `UL851` (چند نام با `-` جدا می‌شوند: `5E42-BR20`) |

> waypointهای ارجاع‌شده در awy باید در `fix.dat` یا `nav.dat` موجود باشند تا
> route-manager بتواند آن‌ها را resolve کند. ~70 هزار قطعه در داده‌ی پیش‌فرض.

## ۷. `poi.dat`

نقاط مورد علاقه از OpenStreetMap (تحت لایسنس ODbL). برای نمایش نام شهر/کشور روی نقشه.

```
# poi.dat v1.02
# ID | LAT | LON | NAME

ID   عرض‌جغرافیایی   طول‌جغرافیایی   نام
────────────────────────────────────────
10   12.7503486    122.7312101   Philippines
12   ...                          (شهر بزرگ)
13   ...                          (شهر کوچک)
14   ...                          (روستا)
```

| کد ID | معنی |
|-------|------|
| `10` | کشور (Country) — 235 عدد |
| `12` | شهر بزرگ (City) — 6596 |
| `13` | شهر کوچک (Town) — 56581 |
| `14` | روستا (Village) — 705597 |

بزرگ‌ترین فایل (~11.8MB فشرده، ~769 هزار خط). برای ناوبری ضروری نیست؛ فقط برچسب‌های
جغرافیایی نقشه.

## ۸. `carrier_nav.dat`

TACAN ناوهای هواپیمابر. چون ناو **متحرک** است، lat/lon ثابت ندارد و با `999`
placeholder پر می‌شود؛ FlightGear موقعیت را به‌صورت پویا از مدل AI ناو می‌گیرد.

```
12  999  999  100 10890   0  0.0  FCH  FNS Foch TACAN
12  999  999  100 10925 300  0.0  NMZ  USS Nimitz TACAN
```

ساختار مثل رکورد نوع `12` در nav.dat، با تفاوت‌ها:
- ستون lat/lon = `999` (موقعیت پویا).
- کانال/فرکانس TACAN، برد (NM؛ مثلاً 300 برای ناوهای US با AN/URN-25).
- شناسه (`NMZ`) و نام (`USS Nimitz TACAN`).

شناسه‌ها به مدل AI ناو وصل می‌شوند تا خلبان بتواند با TACAN ناو را پیدا کند.

## ۹. `TACAN_freq.dat`

جدول نگاشت **کانال TACAN → فرکانس پاسخ (kHz)**. TACAN با شماره‌ی کانال (مثل `109X`)
کار می‌کند نه فرکانس مستقیم؛ این جدول تبدیل را انجام می‌دهد.

```
Channel   Reply_Freq (KHz)
001X      13440
001Y      13445
002X      13450
...
```

| ستون | توضیح |
|------|-------|
| ۱ | کانال TACAN (شماره + `X` یا `Y` برای حالت) |
| ۲ | فرکانس پاسخ بر حسب کیلوهرتز |

~252 کانال. سیستم اویونیک از این برای تنظیم TACAN/DME استفاده می‌کند.

## ۱۰. `range.high` / `range.low` / `range.term`

سه جدول ساده‌ی دو-ستونی که **برد دریافت navaid را تابع ارتفاع** مدل می‌کنند. مطابق
سه «service volume» استاندارد VOR هستند:

| فایل | معادل service volume |
|------|----------------------|
| `range.term` | Terminal (نزدیک فرودگاه) |
| `range.low` | Low altitude (مسیرهای کم‌ارتفاع) |
| `range.high` | High altitude (مسیرهای پرارتفاع) |

فرمت (نمونه از `range.high`):

```
ارتفاع(فوت)   برد(NM)
──────────────────────
0.0           10.0
1000.0        40.0
14500.0       100.0
18000.0       130.0
31500.0       200.0
60000.0       100.0
75000.0       0.0
```

| ستون | توضیح |
|------|-------|
| ۱ | ارتفاع (فوت) |
| ۲ | حداکثر برد دریافت در آن ارتفاع (NM) |

FlightGear بین این نقاط درون‌یابی خطی می‌کند تا تعیین کند آیا یک navaid از موقعیت
فعلی هواپیما قابل دریافت است یا نه (مدل واقع‌گرایانه‌ی خط دید رادیویی — هرچه بالاتر،
برد بیشتر).

## ۱۳. پوشه‌ی `$FG_ROOT/Airports/`

پوشه‌ی `Airports/` جداگانه از `Navaids/` است، اما **هر دو به یک سیستم واحد
(NavDataCache) خوراک می‌دهند**. این پوشه شامل داده‌ی مربوط به **خود فرودگاه‌ها**
(نه navaidهای enroute) است:

```
Airports/
├── apt.dat.gz        ← داده‌ی همه‌ی فرودگاه‌های جهان (باند، taxiway، چراغ، parking)  ~26.8MB
├── apt.dat.ws3.gz    ← نسخه‌ی World Scenery 3.0 (فرمت v1200، حجیم‌تر، ~156MB)
└── metar.dat.gz      ← فهرست ایستگاه‌های هواشناسی METAR
```

### ۱۳.۰.۱ تقسیم کار: Airports در برابر Navaids
| پوشه | چه چیزی | نوع NavDataCache |
|------|---------|------------------|
| `Airports/apt.dat.gz` | فرودگاه‌ها، باندها، taxiway، parking، فرکانس ATC | `apt` |
| `Airports/metar.dat.gz` | فهرست ایستگاه‌های METAR | `metar` |
| `Navaids/nav.dat.gz` | VOR/NDB/ILS/DME/TACAN/Marker | `nav` |
| `Navaids/fix.dat.gz` | فیکس‌های IFR | `fix` |
| `Navaids/awy.dat.gz` | مسیرهای هوایی | `awy` |
| `Navaids/poi.dat.gz` | نقاط جغرافیایی | `poi` |

این دو پوشه **مکمل** هم‌اند: `apt.dat` می‌گوید فرودگاه/باند کجاست، `nav.dat`
می‌گوید ILS/VOR برای رسیدن به آن باند کجاست. هنگام راه‌اندازی، NavDataCache همه را
با هم در یک پایگاه SQLite ادغام می‌کند تا route-manager/ATC/GPS بتوانند به‌صورت
یکپارچه کوئری بزنند (مثلاً «approach به باند 29L مهرآباد» نیازمند هر دو است).

> ⚙️ پوشه‌ی `NavData/` در scenery (بخش ۱۴) می‌تواند **هر دو** را override کند:
> `NavData/apt/` برای فرودگاه، `NavData/nav/` برای navaid.

### ۱۳.۰.۲ `metar.dat.gz` — فهرست ایستگاه‌های هواشناسی
این فایل **هوا را ذخیره نمی‌کند**؛ فقط **فهرست ICAO فرودگاه‌هایی است که گزارش METAR
زنده دارند** (از NOAA). نمونه:

```
# List of airports known to have metar data available
# Generated by create_metar_dat.py ... http://tgftp.nws.noaa.gov/...
AGGH
ANYN
...
OIIE
OIII
```

کاربرد: وقتی حالت هوای «Live/Real weather» فعال است، FlightGear از این فهرست
نزدیک‌ترین ایستگاه دارای METAR را پیدا می‌کند و METAR واقعی آن را دانلود می‌کند.
(~5685 ایستگاه؛ **OIII و OIIE هر دو در فهرست هستند** ✓). اگر فرودگاهی در این فهرست
نباشد، هوای آن از نزدیک‌ترین ایستگاه درون‌یابی می‌شود.

### ۱۳.۰.۳ `apt.dat.ws3.gz`
نسخه‌ی فرمت **v1200** (World Scenery 3.0 / VPB) از همان داده‌ی فرودگاه‌ها، حجیم‌تر و
با جزئیات بیشتر، که با pipeline سینری نسل جدید (procedural/VPB) استفاده می‌شود. برای
سینری کلاسیک (که پروژه‌ی شما با `.stg`/`.btg` استفاده می‌کند) همان `apt.dat.gz`
معمولی مرجع است.

## ۱۴. پوشه‌ی `NavData/` در scenery اختصاصی

این مکانیزم به شما اجازه می‌دهد **بدون دست‌زدن به داده‌ی جهانی**، داده‌ی ناوبری
سفارشی برای منطقه‌ی خودتان اضافه/override کنید. ساختار (از دامپ scenery پروژه):

```
<scenery>/
├── NavData/
│   ├── apt/
│   │   ├── OICC.dat        ← فرودگاه‌های سفارشی (کرمانشاه)
│   │   ├── OIIE.dat        ← (تهران - امام/قدیم)
│   │   └── OIII.dat        ← مهرآباد (نسخه‌ی سفارشی)
│   ├── awy/
│   │   └── awy.dat         ← مسیرهای هوایی سفارشی منطقه
│   ├── fix/
│   │   └── fix.dat         ← فیکس‌های سفارشی
│   ├── nav/
│   │   └── nav.dat         ← VOR/NDB/ILS سفارشی
│   └── poi/
│       └── poi.dat         ← نقاط سفارشی
├── Objects/                ← مدل‌های استاتیک (.stg)
└── Terrain/
```

### ۱۴.۱ قواعد (مستقیم از `findDatFiles()` در سورس)

1. **نام پوشه‌ی زیرمجموعه باید دقیقاً یکی از این‌ها باشد:** `apt`, `awy`, `fix`,
   `nav`, `poi` (و `TACAN_freq`). هر نام دیگری نادیده گرفته می‌شود.
2. هر فایل با پسوند `.dat` یا `.dat.gz` در آن پوشه خوانده می‌شود (به ترتیب الفبایی).
   می‌توانی چند فایل بگذاری (`OIII.dat`, `OIIE.dat`, …) — همه merge می‌شوند.
3. **فرمت داخل این فایل‌ها دقیقاً همان فرمت فایل جهانی متناظر است.** یعنی
   `NavData/apt/OIII.dat` همان فرمت apt.dat (کد 1، 100، 21، …) را دارد، و
   `NavData/nav/nav.dat` همان فرمت nav.dat (کد 2، 3، 4، …).
4. فایل scenery **قبل از** فایل پیش‌فرض جهانی پردازش می‌شود.
5. مسیر scenery باید در `--fg-scenery` یا `/sim/fg-scenery` ثبت شده باشد (یا داخل
   ساختار استاندارد scenery که FlightGear خودکار اسکن می‌کند).

### ۱۴.۲ نکته‌ی مهم درباره‌ی هدر فایل
فایل‌های جهانی یک خط نسخه/لایسنس در ابتدا دارند (`810 Version ...` یا `I` + نسخه).
برای فایل‌های scenery هم بهتر است **همان ساختار هدر را رعایت کنی** (یا حداقل خط
نسخه‌ی سازگار) تا parser درست شروع کند؛ به نمونه‌ی فایل جهانی متناظر نگاه کن و
الگو بگیر.

### ۱۴.۳ کاربرد عملی برای پروژه‌ی OIII
- یک `ILS` سفارشی برای باند 29L مهرآباد که در داده‌ی جهانی نیست → یک رکورد `4`
  (localizer) + `6` (glideslope) در `NavData/nav/nav.dat`.
- یک `VOR` محلی یا فیکس approach سفارشی → `nav.dat` / `fix.dat`.
- تغییر taxiway/parking مهرآباد → ویرایش `NavData/apt/OIII.dat`.

> این روش دقیقاً همان کاری است که scenery حرفه‌ای انجام می‌دهد: ناوبری محلی را
> با خود scenery حمل می‌کند تا مستقل از به‌روزرسانی داده‌ی جهانی باشد.

## ۱۵. تبدیل داده‌ی AIP به FlightGear

این بخش نشان می‌دهد چطور داده‌ی واقعی و به‌روز از **AIP** (Aeronautical Information
Publication — مثل `OIII.pdf`، `OIIE.pdf` سازمان هواپیمایی کشوری ایران) را به
فرمت‌های FlightGear (apt.dat + nav.dat) نگاشت کنیم. نمونه‌ها از خود AIP‌های واقعی
OIII و OIIE استخراج شده‌اند.

### ۱۵.۱ کدام بخش AIP به کدام فایل می‌رود؟

| بخش AIP (AD 2.x) | محتوا | مقصد در FlightGear |
|------------------|-------|--------------------|
| AD 2.2 (Geographical data) | ARP، ارتفاع میدان، MAG VAR | هدر `apt.dat` (کد 1) |
| AD 2.12 (Runway physical) | باندها، THR coords، بیرینگ، ابعاد | باند `apt.dat` (کد 100) |
| AD 2.13 (Declared distances) | TORA/TODA/ASDA/LDA | metadata (یا کد 100) |
| AD 2.18 (ATS comm) | فرکانس TWR/GND/APP/ATIS | فرکانس `apt.dat` (کد 50–56) |
| AD 2.19 (Radio nav & landing) | ILS/VOR/DME/NDB/TACAN | `nav.dat` (کد 2,3,4,6,12,13) |
| AD 2.24 (Charts) | SID/STAR/approach | procedure (LevelD XML — اختیاری) |

## ۱۶. محدودسازی حجم داده برای کارایی

هدف: کاهش داده‌ی جهانی به «فقط فرودگاه‌های هدف + navaid/مسیرهای منتهی به آن‌ها» —
هم به‌روز، هم سبک.

### ۱۶.۱ واقعیت مهم درباره‌ی کارایی (صادقانه)
داده‌ی apt/nav/fix **یک‌بار** هنگام راه‌اندازی به کش SQLite تبدیل می‌شود. بعد از آن،
**FPS و روان‌بودن پرواز به حجم این داده‌ها وابسته نیست** (کش index-شده است). پس:

| محدودسازی داده روی این‌ها اثر دارد | روی این‌ها اثر **ندارد** |
|-----------------------------------|--------------------------|
| ⏱ زمان build اولیه‌ی کش (اولین اجرا) | 🎞 FPS و پرش (stutter) در پرواز |
| 💾 مصرف RAM پایگاه navdata | بار رندر (دوربین/مدل/سینری) |
| 🧹 تمیزی و قابل‌مدیریت‌بودن داده | |

> پس اگر هدف اصلی **رفع پرش (stutter)** در دید برج چنددوربینه است، گلوگاه آنجا
> **رندر** است نه navdata. محدودسازی navdata عمدتاً startup و RAM و نظم را بهبود
> می‌دهد. (برای رفع پرش، به `oiii-camera.xml` و تنظیمات رندر رجوع کن.)

### ۱۶.۲ روش A — فقط override با scenery NavData (توصیه‌شده، کم‌ریسک)
داده‌ی جهانی را دست‌نخورده بگذار و فقط نسخه‌ی دقیق فرودگاه‌های هدف را در
`<scenery>/NavData/{apt,nav,fix}/` بگذار. مزایا: به‌روزرسانی بدون شکستن جهان،
بازگشت‌پذیر، و داده‌ی شما اولویت دارد. این بهترین گزینه برای دقت AIP است.

### ۱۶.۳ روش B — جایگزینی داده‌ی جهانی با نسخه‌ی منطقه‌ای (برای سبک‌سازی واقعی)
اگر می‌خواهی کل پایگاه را به منطقه‌ی ایران محدود کنی:

1. **`apt.dat` را فیلتر کن** — فقط فرودگاه‌های موردنظر را نگه دار. هر فرودگاه از خط
   `1`/`16`/`17` تا قبل از `1`/`16`/`17` بعدی (یا `99`) یک بلوک است. ابزار نمونه:
   ```bash
   # نگه‌داشتن فقط فرودگاه‌های ایران (ICAO با OI شروع می‌شوند)
   zcat apt.dat.gz | awk '
     /^(1|16|17) / {keep = ($5 ~ /^OI/)}
     keep || /^I$/ || /Version/ {print}
     END{print "99"}' > apt_iran.dat
   gzip apt_iran.dat && mv apt_iran.dat.gz $FG_ROOT/Airports/apt.dat.gz
   ```
2. **`nav.dat` را به محدوده‌ی جغرافیایی فیلتر کن** (مثلاً lat 25–40، lon 44–64):
   ```bash
   zcat nav.dat.gz | awk 'NR<=2 || ($2>25 && $2<40 && $3>44 && $3<64) {print}' > nav_iran.dat
   ```
3. **`fix.dat` و `awy.dat`** را هم به همان محدوده فیلتر کن تا فقط فیکس/مسیرهای
   منطقه بمانند (واژه‌های ارجاع‌شده در awy باید در fix بمانند، وگرنه warning).
4. **`poi.dat`** را می‌توان تقریباً خالی کرد (فقط برچسب نقشه؛ بی‌خطر).

> ⚠️ همیشه **نسخه‌ی پشتیبان** از فایل‌های اصلی بگیر. فیلتر اشتباه awy می‌تواند
> مسیرها را بشکند. برای حفظ سلامت، روش A (override) امن‌تر از روش B (جایگزینی) است.

### ۱۶.۴ روش C — فقط فرودگاه‌های لازم را سینری کن
بزرگ‌ترین صرفه‌جویی واقعی در **سینری/`.btg`** است نه navdata: فقط tileهای منطقه‌ی
OIII را نصب کن (که پروژه‌ی شما با `Scenery_OIII` همین کار را کرده). این هم RAM و هم
زمان لود را به‌شدت کم می‌کند.

## ۱۷. WED، فایل‌های `.btg` و TerraGear

این بخش به یک سوءتفاهم رایج پاسخ می‌دهد: **«اگر apt.dat را تغییر دهم (مثلاً چراغ
باند)، بدون خروجی‌گرفتن از WED اثر می‌کند؟»**

### ۱۷.۱ نقش هر ابزار/فایل
| مؤلفه | چیست | برای چه شبیه‌سازی |
|-------|------|------------------|
| **WED** (WorldEditor) | ویرایشگر گرافیکی فرودگاه؛ خروجی‌اش **متن `apt.dat`** است | ابزار X-Plane (اما apt.dat قابل‌استفاده در FG) |
| **apt.dat** | توصیف متنی فرودگاه (باند، taxiway، چراغ، parking) | هم X-Plane هم FlightGear |
| **TerraGear** (`genapts`) | داده‌ی apt.dat را به مش سه‌بعدی **`.btg`** «بِیک» می‌کند | فقط FlightGear |
| **`.btg`** (Binary TerraGear) | مش سینری باینری: سطح باند/taxiway + **چراغ‌های بِیک‌شده** | FlightGear |
| **`.stg`** | فایل متنی که `.btg` و آبجکت‌های استاتیک را در tile می‌چیند | FlightGear |

### ۱۷.۲ تفاوت بنیادی X-Plane و FlightGear
- **X-Plane:** apt.dat را **در زمان اجرا** می‌خواند و فرودگاه (شامل چراغ‌ها) را
  زنده رندر می‌کند. پس ویرایش apt.dat در WED → اثر فوری روی چراغ‌ها، **بدون** هیچ
  مرحله‌ی بِیک.
- **FlightGear (سینری کلاسیک WS2.0 — همان که پروژه‌ی شما دارد):** apt.dat **دو
  مصرف‌کننده‌ی جدا** دارد:

```
                    ┌─────────────────────────────────────────────┐
                    │                 apt.dat                     │
                    └───────────────┬─────────────┬───────────────┘
                                    │             │
              (زمان اجرا)            │             │   (زمان ساخت سینری، آفلاین)
                                    ▼             ▼
                        ┌──────────────────┐   ┌────────────────────────┐
                        │  NavDataCache    │   │  TerraGear genapts      │
                        │  (SQLite)        │   │  → airport .btg         │
                        ├──────────────────┤   ├────────────────────────┤
                        │ • وجود باند/THR  │   │ • مش سطح باند/taxiway   │
                        │ • ILS/ATC منطق   │   │ • چراغ‌های بِیک‌شده       │
                        │ • شبکه‌ی AI ground│   │ • نشانه‌گذاری/خطوط       │
                        │ • منطق PAPI/approach│ │ (بصریِ ثابت)            │
                        └──────────────────┘   └────────────────────────┘
```

### ۱۷.۳ پاسخ مستقیم به سؤال
**اگر فقط apt.dat را تغییر دهی (مثلاً چراغ باند) و TerraGear را دوباره اجرا نکنی:**

| لایه | تغییر می‌کند؟ |
|------|----------------|
| **منطقی/navdata** (وجود باند، THR، ILS، ATC، شبکه‌ی AI، منطق PAPI) | ✅ **بله** — بعد از rebuild کش navdata |
| **بصریِ بِیک‌شده** (چراغ‌های واقعی که در صحنه می‌بینی، مش باند) | ❌ **خیر** — تا وقتی `.btg` را با `genapts` بازنسازی |

یعنی **چراغ‌های باندی که در صحنه می‌بینی، در `.btg` پخته شده‌اند** (توسط
`TerraGear/src/Airports/GenAirports/lights.cxx`). صرفِ ویرایش apt.dat آن‌ها را عوض
نمی‌کند؛ باید:
1. apt.dat را ویرایش کن،
2. `genapts850` (از TerraGear) را برای آن tile اجرا کن تا `.btg` جدید بسازد،
3. `.btg` جدید را جایگزین فایل سینری کن.

### ۱۷.۴ پس WED برای FlightGear چه نقشی دارد؟
- WED فقط یک **ویرایشگر apt.dat** است؛ خودش `.btg` نمی‌سازد.
- گردش‌کار FlightGear: **WED (ویرایش) → apt.dat → TerraGear `genapts` (بِیک) →
  `.btg` → نصب در سینری.**
- خروجی apt.dat از WED به‌تنهایی، فقط لایه‌ی **منطقی** را (پس از قرارگرفتن در
  `NavData/apt/` و rebuild کش) تغییر می‌دهد، نه ظاهر بِیک‌شده را.

### ۱۷.۵ استثناء: سینری نسل جدید (WS3.0 / VPB)
در pipeline جدید (apt.dat v1200 + VPB/procedural)، بخشی از فرودگاه می‌تواند در زمان
اجرا تولید شود (شبیه X-Plane). اما پروژه‌ی شما با سینری کلاسیک `.stg`/`.btg` کار
می‌کند، پس قاعده‌ی بالا (نیاز به بِیک مجدد برای تغییر بصری) برقرار است.

> 💡 جمع‌بندی عملی برای پروژه‌ی OIII: برای تغییرات **عملکردی** (ILS جدید، فرکانس،
> شبکه‌ی ground برای AI) فقط `NavData/` را ویرایش و کش را rebuild کن. برای تغییرات
> **دیداری** باند/چراغ/taxiway، باید از TerraGear خروجی `.btg` بگیری.

## ۱۸. گردش‌کار ویرایش و بازسازی کش

1. **فایل را از حالت gz خارج کن** (در صورت نیاز): `gunzip -k nav.dat.gz`.
2. ویرایش با ادیتور متنی ساده — **ستون‌بندی را به‌هم نزن** (فرمت فاصله‌محور است؛
   بعضی parserها به موقعیت ستون حساس‌اند، اکثراً به جداکننده‌ی فاصله/تب).
3. (اختیاری) دوباره فشرده کن: `gzip nav.dat`.
4. شبیه‌ساز را اجرا کن — چون modtime/اندازه عوض شده، NavDataCache خودکار rebuild
   می‌کند (پیام «Rebuilding navigation database»).
5. اگر rebuild اتفاق نیفتاد، کش را دستی پاک کن:
   - مسیر کش: `$FG_HOME/navdata.cache` (یا `navdata_<hash>`).
   - حذفش کن تا اجرای بعد از صفر بسازد.

### اشکال‌زدایی
- `--log-level=info` + کانال `SG_NAVCACHE`: گزارش می‌دهد چه فایل‌هایی اسکن و چرا
  rebuild شد.
- برای تست اینکه navaid لود شده: dialog **Equipment → Radio** یا **Map**، یا
  property `/instrumentation/nav[0]/...` را در property browser چک کن.
- شناسه‌های تکراری یا فیکس‌های ارجاع‌نشده در awy می‌توانند warning بدهند.

### اشتباهات رایج
| مشکل | علت |
|------|-----|
| navaid سفارشی دیده نمی‌شود | نام پوشه غلط (مثلاً `NavData/navs/` به‌جای `NavData/nav/`) |
| کش rebuild نمی‌شود | تغییر فقط در محتوای کش‌شده بدون تغییر modtime؛ کش را دستی پاک کن |
| باند/فرودگاه ناقص | کد رکورد یا تعداد ستون اشتباه؛ با نمونه‌ی واقعی کراس‌چک کن |
| فرکانس غلط | یادآوری: VOR/ILS بر حسب ده‌هزارم MHz (`11670`=116.70)، NDB بر حسب kHz |
| ILS بدون glideslope | فراموش‌کردن رکورد `6` (GS) — فقط `4` کافی نیست |
